# Audit — reproductibilité "fresh clone → nouveau dataset → release sc-crop"

> **Mise à jour 2026-07-14 (réaudit)** : tous les points de la section 8 (priorisation) ont été corrigés sur cette branche. Voir "Réaudit" en bas de fichier pour le détail de ce qui a changé et ce qui reste ouvert.

Date : 2026-07-14. Branche : `qr/cleaning-repo`. Périmètre : ce dépôt (entraînement détecteur + classifieur) et son interaction avec `sc-crop` (package consommateur).

Question testée : un nouvel arrivant, avec juste `git clone`, peut-il ajouter un dataset, réentraîner les deux modèles, et publier une nouvelle version de `sc-crop` en peu de clics ? **Non, pas aujourd'hui.** Le pipeline de calcul fonctionne, mais la doc est désynchronisée du code, il n'y a pas une commande mais deux à lancer manuellement (détecteur puis classifieur), et la release finale dépend d'un chemin absolu et d'un versioning à la main.

## 1. Ce qui marche déjà bien

- **Ajout de dataset** : entrée dans `configs/datasets.yaml` (nom, host, url, commit, `mask_suffix`, `img_glob`...) suffit pour les hosts git-annex. Pour un host hors git-annex (ex. Zenodo), il faut écrire un `scripts/download_<name>.sh` (pattern déjà suivi pour TotalSegmentator). C'est un vrai point fort : la logique de découverte est déclarative, pas de fallback caché.
- **Pipeline config-driven** : `scripts/run_pipeline.py` (un seul point d'entrée réel) lit `configs/{preprocess,training_dataset,training,evaluation}.yaml`, snapshote la config dans `runs/<TS>/configs/`, exécute 9 étapes (download → preprocess → splits → build dataset → train → evaluate → metrics → plots → failures), dispatche détection/classification selon `training.yaml: mode`.
- **Traçabilité par run** : `run_info.yaml` (git hash + dirty flag), config snapshotée, warning explicite si repo dirty. Bonne base pour la reproductibilité.
- **Export → sc-crop** : `scripts/export_model.py` + `scripts/release.sh` couvrent tout le chemin (export ONNX, SHA256, release GitHub sur `ivadomed/sc-crop`, tag des deux dépôts, mise à jour de `download.py` et `VERSIONS.md`, bump de version, commit+push). Le format attendu côté `sc-crop` (ONNX + SHA256 + `config.yaml` inférence) est documenté et cohérent des deux côtés.

## 2. Le vrai problème : deux modes, une seule commande documentée

`training.yaml: mode: detection|classification` sélectionne le mode. **Aucune commande ne lance les deux entraînements.** Il faut : éditer `training.yaml` → lancer `run_pipeline.py` → éditer à nouveau `training.yaml` → relancer. C'est exactement ce qui s'est passé sur la branche courante avant cet audit (`training.yaml` avait `mode` modifié en local, non committé). Le "bouton unique" attendu par l'utilisateur n'existe pas — il faudrait un wrapper qui lance les deux modes à la suite dans deux run-dirs, avant d'appeler `export_model.py`.

## 3. Documentation désynchronisée du code (à corriger en priorité)

- **README.md** (§"Automatic pipeline", ~l.169-198) décrit un `scripts/run_pipeline.sh` avec des variables éditables en tête de fichier (`PLANE`, `MAKE_SPLITS`, `SEED`, `DATASET_FACTORS`, `MODEL`, `EPOCHS`...). Le fichier réel (`scripts/run_pipeline.sh`) ne fait que 3 lignes utiles et forward `--run-dir/--start/--end/--no-wandb/--require-clean` à `run_pipeline.py`. **Cette section entière est fausse.**
- **README.md** (§"Step-by-step pipeline", ~l.200-304) référence `scripts/infer.py`, `scripts/reconstruct.py`, `scripts/border_metrics.py` — **ces fichiers n'existent pas** dans `scripts/`. La table `METRIC_LABELS`/`iou_gt_mean`/`iou_all_mean` (l.290-293) référence des métriques qui viennent d'être retirées du code (§5).
- **README.md** step-by-step ne documente que le détecteur, jamais le classifieur (`build_class_dataset.py`, `evaluate_cls.py` absents du README alors qu'ils sont dans `run_pipeline.py`).
- **CLAUDE.md** (projet) référence lui aussi `infer.py`, `reconstruct.py`, `border_metrics.py` comme scripts existants, avec une hiérarchie de sortie détaillée pour des fichiers absents du repo.
- **Aucune section README pour "ajouter un dataset"** alors que le mécanisme existe et fonctionne (`configs/datasets.yaml`). C'est le premier truc qu'un nouvel arrivant cherchera — actuellement il doit lire `preprocess.py`/`download_all_datasets.sh` pour le deviner.

## 4. Fragilité de la release vers sc-crop

- `scripts/release.sh` a `SCCROP_REPO="/home/quentinr/sc-crop"` en dur — cassé pour toute autre machine/utilisateur.
- Versioning manuel : `MODEL_VERSION`/`PACKAGE_VERSION` à éditer à la main en tête de script. Déjà pris en défaut sur la branche courante : le brouillon local avait `0.0.9`/`0.1.9` alors que `sc-crop/VERSIONS.md` référence déjà `v0.0.10` comme dernier modèle publié — dérive silencieuse, pas de garde-fou qui vérifie la cohérence avant de lancer.
- Suppose `gh` authentifié + droits d'écriture sur `ivadomed/sc-crop` + clone local du dépôt sc-crop au chemin exact — aucune vérification préalable (`gh auth status`, existence du dossier) dans le script.
- Côté `sc-crop` : `CHANGELOG.md` décrit encore un ancien flux (release zip + variable `_RELEASE_URL` dans `download.py`) qui ne correspond plus au mécanisme actuel (dict `_ASSETS` avec SHA256 par fichier, pas de `_RELEASE_URL`). Un nouvel arrivant qui suit `CHANGELOG.md` à la lettre suivra une procédure obsolète.
- Changement API cassant non versionné en `major` : `sc_crop/qc.py` (`check_seg_truncation`) change ses clés de retour (`pad_superior/pad_inferior/...` → `xmin/xmax/...`) dans un bump *mineur* `0.6.0→0.7.0`. `ARCHITECTURE.md` liste déjà "breaking change non versionnée" comme problème connu — ça se reproduit ici, en cours d'audit.
- Aucune CI, aucun test automatisé ni côté `model_cropping` ni côté `sc-crop`. La cohérence version package/version modèle n'est vérifiée qu'au moment de `publish.sh` (PyPI), jamais avant.

## 5. Nettoyage des métriques — fait sur cette branche

Conformément à la demande : gardé uniquement `iou_3d_mm` (IoU 3D en mm³) et `gap_mm_R/L/P/A/I/S` (padding signé par face, mm) — plus `gap_mm_S`/`gap_mm_I` côté classifieur.

Supprimé de `scripts/metrics.py` (1105→266 lignes), `scripts/plot_metrics.py` (511→347), `scripts/find_failures.py` (496→269) : IoU 2D (`iou`, `iou_nearest_gt`, `iou_gt_mean`, `iou_all_mean`), taux FP/FN, `iou_3d` voxel, `iou_sc_mid_box`, et tous les variants expérimentaux d'ablation (`_trim*`, `_graphreg`, `_facetrim`, `_reg30mm`, `_ransac`, `_filt`, `_pad10`, `_padz20`, `_clsfilt`, `_clscomp`) ainsi que le rapport AP/FP/FN (`ap_at_iou`, `build_report`). `scripts/evaluate_cls.py` n'a pas eu besoin de changement (déjà scopé à `gap_mm_S/I`). `run_pipeline.py`/`evaluate.py` vérifiés sans référence pendante. `py_compile` OK sur tous les fichiers touchés.

**Non touché volontairement** (hors périmètre demandé) : `experiments/experiment_detector.py`, `scripts/2d_*_stats.py` — utilisés pour le papier/l'exploration de design, pas pour l'entraînement de production.

Reste à faire : `CLAUDE.md` (section metrics.py) a été mis à jour par la simplification, mais README.md §"Step-by-step pipeline" (Step 8, table des métriques) référence encore `iou_gt_mean`/`iou_all_mean` — à corriger en même temps que le reste de la doc (§3).

## 7. Dette de dépendances

`requirements.txt` : `torch`/`torchvision` pinnés, reste en bornes `>=` lâches. Pas de lockfile, pas de `pyproject.toml`, pas d'`environment.yml`. `CLAUDE.md` pin `ultralytics 8.4.23` en dur alors que `requirements.txt` autorise `>=` — deux sources de vérité qui peuvent diverger silencieusement. Aucun test, aucune CI des deux côtés (`model_cropping` et `sc-crop`).

## 8. Priorisation suggérée

1. Sécuriser `.gitignore` (§6, dernier paragraphe) avant tout commit — risque concret de gros commit accidentel.
2. Réécrire README.md §"Automatic/Step-by-step pipeline" pour matcher `run_pipeline.py` réel, ajouter la classification, ajouter "ajouter un dataset".
3. Supprimer les références mortes dans `CLAUDE.md` (`infer.py`, `reconstruct.py`, `border_metrics.py`).
4. Wrapper "un bouton" : script qui lance les deux modes (`detection` puis `classification`) à la suite et appelle `export_model.py` en sortie.
5. `release.sh` : remplacer le chemin absolu par une variable d'env/détection, ajouter une vérification de cohérence de version avant publication (lire `VERSIONS.md` de `sc-crop` au lieu de bumper à l'aveugle).
6. `sc-crop/CHANGELOG.md` : réécrire pour matcher le mécanisme `_ASSETS`/SHA256 actuel.
7. Nettoyer les branches mortes (`feat/yaml-datasets`, `feat/2-class-stratified`, `feat/config-files`, `feat/sagittal-model`).
